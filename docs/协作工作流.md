# 协作工作流

> 本文件把团队的协作工作流收敛成可执行约定。
> 分支/提交/PR 的基础规范见 [`CLAUDE.md`](../CLAUDE.md);本文件聚焦**怎么跑这套流程**,以及针对本项目(2 人、各用各的 Claude、两条带交接点的线)的补充约定。

---

## 采用的工作流:GitHub Flow(功能分支流)

为什么是它:小团队 / 新手的业界共识。`main` 永远可用,所有改动走短命分支 + PR。
- ❌ 不用 **Git Flow**(多条长命分支),对我们过度复杂。
- ❌ 暂不用 **Trunk-Based**(直推 main),它依赖强 CI/自动化测试,我们还没有。
- ✅ 有了 CI 之后,可再考虑向 trunk-based 演进。

## 标准流程(每个任务的循环)

1. 在 GitHub **认领 / 新建 Issue**,确认在做哪件事。
2. 从最新 `main` 开**功能分支**:`git checkout main && git pull && git checkout -b 名字/功能简述`。
3. 动手前**先说计划**(spec-first),小步提交,commit 信息写清楚做了什么。
4. 完成后提 **draft PR**,描述里关联 Issue(`Closes #x` 或 `关联 #x`)。
5. **请对方 review**(见下),改完 → 再推 → 对方 approve。
6. **Squash 合并**进 `main`,删分支。
7. 进展记到 `docs/想法与进度.md`。

## 互相 review(2 人协作的核心)

- **每个 PR 由另一个人 review 后再合**,而不是自己合自己的。
  - Lihong 的 PR → Nicky review;Nicky 的 PR → Lihong review。
- review 看:逻辑对不对、是否偏离方向、有没有更简单的做法;看不懂的地方直接在 PR 上问。
- 例外:纯文档 / 紧急修复,可自行合并,但事后知会对方。
- (注:项目搭建初期由 owner 直接合并是临时的,正式开发后切换到互相 review。)

## 目录分线(降低冲突)

两条线放在各自目录,几乎不碰同一文件:

```
/reproduction   # Lihong:技术复现 + 成本测算代码、notebook
/report         # Nicky:行业报告、数据、分析
/docs           # 共享:路线图、想法与进度、本工作流
```

## 交接接口契约(M2 / M3 的关键)

两条线在里程碑 **M2 / M3** 交接「成本数据」。交接前**先约定格式**,避免对不上:

- 约定一个固定 schema 的文件(如 `report/data/costs.csv` 或 `.json`),字段先定义好:
  - 例:`model, stage(推理/训练), gpu_type, gpu_hours, est_cost_usd, source(实测/公开/估算), assumptions`
- Lihong 按这个 schema 填,Nicky 直接读;字段要变先在 Issue/PR 里说一声。
- **区分来源**:实测 / 公开 / 估算 三类标清(见路线图)。

## 共享文件约定

`docs/想法与进度.md` 是唯一两人都常改的文件:
- **只追加,不改别人写的**;各自在对应小节(已确定的决定 / 想法清单 / 进度日志)末尾加。
- 这样基本不会有合并冲突。

## CI(代码落地后再加,Issue #3)

AI 写的代码尤其需要自动把关。等技术线有了可跑代码:
- 每次 PR 自动跑测试 + lint(如 ruff / black)。
- 详见 web 会话的 SessionStart hook 配置(可让 Claude 帮忙搭)。

## 各用各的 Claude 的约定

- **`CLAUDE.md` 是两个 Claude 的共享规则库**:都先读它,行为才一致;规则尽量明确、给例子。
- **spec 先行**:动手前把要做的写清楚再让 Claude 写(已在工作准则里)。
- **换手时喂上下文**:让接手的 Claude 先看最近的 commit、相关 PR 和 docs,再开工。
